# Docs Reorganization Design

## Goal

Reorganize `docs/` into a stable documentation system that serves onboarding, day-to-day development, and historical traceability at the same time, while reducing noise in the main entry points.

## Current Problems

- `docs/` mixes stable guidance, temporary notes, experiment records, batch run outputs, and change logs in the same visible surface.
- `docs/INDEX.md` currently exposes archival material and scratch records alongside primary documentation.
- `docs/index.md` and `docs/INDEX.md` both exist, but their roles are not clearly separated.
- `python scripts/doc_manager.py --validate` currently reports missing or incomplete front matter in multiple files.
- Naming and placement are inconsistent: some files are organized by audience, some by implementation detail, and some by the moment they were written.

## Design Summary

The new structure uses two documentation layers plus two distinct entry files.

### Layer 1: Primary Docs

Primary docs are the current, user-facing, long-lived documents. They should answer one of these questions:

- How do I get started?
- How do I perform a task?
- How does the system work?
- Where is the reference material?
- How do I operate or maintain the workflow now?

Proposed stable directories:

- `docs/getting-started/`
- `docs/how-to/`
- `docs/architecture/`
- `docs/reference/`
- `docs/operations/`

Only documents with durable value and reusable guidance belong here.

### Layer 2: Records

Records capture dated, contextual, experimental, or stage-specific material. These documents remain important for traceability, but they should not dominate the main navigation.

Proposed record directories:

- `docs/records/changes/`
- `docs/records/research/`
- `docs/records/runs/`
- `docs/records/archive/`

This layer absorbs most material currently under `changes/`, `research/`, `test0_full/`, `test0_smoke/`, and `tmp/`.

## Entry Points

### `docs/index.md`

This becomes the curated human landing page. It should stay short and point to:

- onboarding and quickstart material
- the most common task-oriented guides
- the most important architecture and reference pages
- current operations/runbook documents
- the records layer for historical investigation

It should not enumerate every document in the repository.

### `docs/INDEX.md`

This remains the generated full catalog. It should be regenerated by `scripts/doc_manager.py`, but the output should be structured in a way that clearly separates:

- `Primary Docs`
- `Records`

Within those top-level groups, documents can still be grouped by directory.

## Migration Rules

Migration is based on document role, not on the current folder name.

### Move to Primary Docs

- `overview/` material and top-level onboarding content move into `getting-started/`
- task-oriented content from `usage/` moves into `how-to/`
- reusable examples from `examples/` move into `how-to/` or a scoped subdirectory beneath it
- explanatory system design stays in `architecture/`
- module, script, and tool guides from `modules/`, `scripts/`, `specs_normalizer/`, `references/`, and part of `specs/` move into `reference/`
- stable FAQ content is folded into `getting-started/` or `reference/`, rather than preserved as a separate top-level silo
- durable DLC usage and operations guides stay in the primary layer, typically under `operations/` or `reference/`, depending on whether the document is procedural or descriptive
- durable runbooks and maintenance procedures remain under `operations/`
- top-level standalone docs are explicitly relocated: `MAINTENANCE_WORKFLOW.md` moves into `operations/`, and team/process playbooks such as `agent-team-playbook.md` move into `operations/` as well, instead of remaining at `docs/` root

### Move to Records

- `changes/` moves under `records/changes/`
- `research/` moves under `records/research/`
- dated or failure-analysis material under `dlc/` moves into `records/` when it is batch-specific rather than evergreen
- `test0_full/` and `test0_smoke/` move under `records/runs/`
- `tmp/` and similar scratch or one-off notes move under `records/archive/`

### Classification Rule for Ambiguous Files

If a document depends on a specific batch, experiment, run date, investigation phase, or temporary context, it defaults to `records/`.

A document is promoted to the primary layer only if it is:

- reusable without special batch context
- expected to stay relevant after the current effort ends
- useful as a stable entry point for future readers

## Naming Rules

- Directory names use English lowercase kebab-case.
- Stable docs avoid date prefixes unless the date is part of the subject itself.
- Record docs keep date or batch identifiers when those identifiers are essential context.
- Chinese content may remain in the body or title, but paths should be standardized.
- Bilingual pairs remain colocated and use consistent suffixes such as `.zh-CN.md`.

## Metadata and Index Generation

The existing front matter validation stays in place, and the documentation workflow gains one lightweight classification field:

```yaml
doc_class: primary | record | archive
```

This field is used to:

- separate curated docs from historical material in generated indexes
- support future governance without relying only on directory names
- keep the main documentation surface intentionally small

The existing required metadata remains mandatory:

- `title`
- `created_at`
- `updated_at`
- `maintainer`

`code_reference` remains recommended and should be normalized consistently.

## Governance Rules

- New evergreen docs go to the primary layer.
- New investigations, handoffs, run notes, and stage snapshots go to the records layer.
- Missing front matter must be fixed during migration.
- Duplicate-topic documents do not need immediate full content merges, but each topic should have one clear primary entry point.
- Historical documents may stay separate if they add traceability, but they should be demoted out of the main entry surface.

## Acceptance Criteria

The reorganization is complete when all of the following are true:

1. `python scripts/doc_manager.py --validate` passes.
2. `python scripts/doc_manager.py --gen-index` generates a clean `docs/INDEX.md` without manual patching.
3. `docs/index.md` acts as a concise curated entry page.
4. `docs/INDEX.md` clearly separates primary documentation from records.
5. The current known metadata issues are resolved.
6. `tmp/`, run outputs, and dated investigations no longer dominate the primary navigation surface.
7. Ambiguous or duplicate documents have an explicit keep/demote/archive decision.

## Non-Goals

- Rewriting all technical content for style consistency
- Substantive technical re-authoring of documents unrelated to structure
- Collapsing all historical records into a single merged narrative
- Expanding the documentation tooling beyond the minimum needed to sustain the new structure

## Risks and Controls

### Risk: Broken internal links after large moves

Control:

- update internal Markdown links during migration
- regenerate index only after moves are complete
- verify landing pages and known cross-links after restructuring

### Risk: Primary docs becoming noisy again

Control:

- enforce `doc_class`
- keep `docs/index.md` curated rather than exhaustive
- default ambiguous files to `records/`

### Risk: Reorganization turns into broad content rewriting

Control:

- limit edits to structure, naming, front matter, local framing text, and cross-references
- leave deep content revision for separate follow-up work

## Implementation Boundaries

This effort includes:

- directory restructuring
- document reclassification
- file renaming where needed
- front matter repair
- index generation changes
- internal navigation cleanup

This effort does not include:

- broad changes to code behavior
- non-documentation repository cleanup
- rewriting every existing document into a unified style guide

## Recommended Next Step

Write an implementation plan that executes the reorganization in controlled phases: inventory and mapping, directory creation, file migration, metadata repair, index/tooling updates, navigation cleanup, and final validation.
